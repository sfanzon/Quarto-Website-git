# AGENTS.md

## Purpose

Instructions for coding agents working on `sfanzon/Quarto-Website-git`.

For non-trivial work, also read:

- `SOURCE_MAP.md` — source-ownership reference ("which file do I edit?")
- `ARCHITECTURE.md` — source ownership and implementation architecture
- `DESIGN.md` — visual identity and editorial rules
- `README.md` — build, test and repository orientation

## Core rules

1. **Agents may modify any source needed to complete the task.**
2. **Preserve the existing visual identity.** Do not redesign unrelated parts of the site.
3. **Use canonical sources.** Do not fix source problems by editing generated output.
4. **Prefer coherent architectural fixes over additional patches or overrides.**
5. **Do not overwrite unrelated user changes.**
6. **Stop when the requested task is complete.** Do not continue into optional cleanup, redesign, refactoring or additional improvements unless they are necessary for correctness.

## Planning

For trivial changes, act directly.

For medium or large changes:

1. inspect the relevant implementation;
2. identify the source of truth and shared dependencies;
3. state a concise plan;
4. implement;
5. validate proportionally to the change;
6. inspect the final diff.

Examples requiring a plan:

- navigation changes;
- shared component changes;
- project-page restructuring;
- CSS architecture refactors;
- data-schema changes;
- build/deployment changes;
- broad responsive work.

Do not create a large plan for a small, local change.

## Source Files vs Generated Output

Always modify the canonical source responsible for the requested behaviour.

Before making a website change:

1. identify the real source of the behaviour:
   - Quarto source (`.qmd` files, `_quarto.yml`);
   - hand-written or generated includes (`includes/`);
   - SCSS/CSS source (`styles/`);
   - structured data (`data/`);
   - Lua filters (`filters/`);

2. never directly edit generated files as the implementation:
   - `docs/*.html`;
   - generated Quarto output;
   - hashed CSS/JS bundles;
   - generated Bootstrap assets.

For changes that affect rendered output or the generation pipeline:

- run the appropriate render/build command;
- allow generated output to update;
- commit generated files only if this repository workflow requires them.

A valid implementation must change the canonical source responsible for the behaviour. A commit containing only regenerated HTML/assets is not a valid implementation.

When reviewing your own work:

- confirm the intended source files changed;
- confirm generated output changed when rendering was relevant;
- do not assume regenerated files mean the feature was implemented correctly.

Do not render the entire site merely because a documentation-only or otherwise non-rendered source file changed.

## Scope discipline

Fix closely related issues when necessary for the requested result.

Do not turn a local task into an opportunistic redesign, cleanup or refactor.

Prefer a coherent fix over layering another patch, but keep the solution proportional to the task.

Do not modify unrelated files merely because they could also be improved.

## Maintainability and code budget

The Astro migration must reduce implementation complexity, not reproduce the
roughly 7,000-line SCSS accumulation of the previous Quarto implementation.
Keep authored code minimal, explicit and auditable.

Minimise **architectural / semantic complexity, not physical line count**.
Human-readable source takes priority over artificially small LOC: use normal
indentation and multiline nested markup, do not combine unrelated statements
or logical elements merely to shrink a diff, and do not compress source as a
project goal. Formatting-only line growth is not substantive complexity; the
CSS/JS review signals below concern meaningful implementation complexity.

- Give every visible component and behaviour one obvious canonical owner.
- Edit that owner rather than adding override layers, catch-all
  `patch`/`fix`/`misc` stylesheets, or compensating rules.
- When ownership moves, delete obsolete or transitional implementations unless
  they remain explicitly required during the migration.
- Do not duplicate Astro and Quarto implementations when a shared owner can
  serve the final hybrid site.
- Do not add abstractions, frameworks or dependencies without a demonstrated
  need that outweighs their maintenance cost.
- Keep component and page styles with their narrow owners; do not let them
  accumulate into a global monolith. Every file must have a narrow,
  explainable responsibility.
- Keep `SOURCE_MAP.md` sufficient for a maintainer to answer: “what controls
  this?”
- If a task requires substantial code growth, reconsider the design and
  simplify before adding it.

Code size is a review signal, not a quota. Around **+150 lines of authored
CSS/JS** in one task requires an explicit complexity review. An authored
CSS/JS file approaching or exceeding **~500 lines** requires review of whether
its responsibilities should be split. In both cases, explain why the added
complexity is necessary or reduce it before completion.

Before declaring a substantial implementation task complete, check whether it:

- introduced an override rather than changing the owner;
- duplicated behaviour across renderers or components;
- retained obsolete code after an ownership move;
- obscured ownership in `SOURCE_MAP.md`; or
- added code disproportionate to the requested behaviour.

## Design

Read `DESIGN.md` before visual work.

Treat `DESIGN.md` as the canonical design reference unless the user explicitly asks to change the design.

Hard constraints:

- warm editorial visual identity;
- restrained rust/warm accent system;
- compact typography;
- light and dark modes;
- mixed professional audience;
- applied mathematics as the foundation, applications as the evidence;
- no generic data-science, SaaS, AI-startup, or academic-template redesign.

Preserve the project-page hierarchy defined in `DESIGN.md`.

Current width system:

- Site shell: **1180 px**
- General reading / mixed content: **820 px**
- Sustained prose: **720 px**

Use the width appropriate to the content type, not mechanically to the page name.

## CSS / Quarto

Use the existing token and component system.

Prefer:

- shared variables;
- component-scoped rules;
- semantic HTML;
- structural fixes;
- Quarto-native features when suitable.

Avoid:

- duplicate component implementations;
- new override layers when the canonical owner can be fixed directly;
- chains of `!important`;
- arbitrary pixel nudges without understanding the layout;
- unnecessary JavaScript;
- rebuilding working Quarto functionality.

Move ownership deliberately:

1. identify the canonical owner;
2. move or fix the rule there;
3. verify the result;
4. remove the obsolete definition.

Do not leave parallel implementations behind.

## Build

Preview:

```bash
quarto preview
```

Render:

```bash
quarto render
```

The pre-render hook runs `scripts/build-content.py`.

Render when the task affects the rendered site, generated content or build pipeline.

A documentation-only change does not require a Quarto render unless it affects build behaviour.

If Quarto or another required build tool is unavailable, validate what can be validated and report the limitation explicitly.

## Tests

Use the **smallest validation set that gives meaningful confidence for the change**.

Do not run every available test merely because a source file changed.

### Small or local changes

Use:

```bash
npm run test:quick
```

Appropriate for:

- small CSS changes;
- local content/source changes;
- simple interactions;
- static checks;
- narrow bug fixes.

### Broader functional changes

Use:

```bash
npm test
```

Appropriate for:

- shared behaviour changes;
- navigation or interaction changes;
- changes affecting multiple pages;
- broader pre-release validation.

### Visual changes

Use:

```bash
npm run test:visual
```

when the rendered appearance may have changed materially.

Do not update visual baselines merely to make tests pass.

Use:

```bash
npm run visual:baseline
```

only for an intentional visual change that has been inspected and accepted.

### Broad structural or browser-sensitive changes

Use:

```bash
npm run test:full
```

for changes such as:

- broad responsive work;
- CSS architecture changes with wide impact;
- shared layout restructuring;
- browser-sensitive interaction changes;
- major refactors affecting many pages.

The full suite is not the default validation step.

If a relevant test cannot be run, state this explicitly.

## Visual validation

For visual/layout work, inspect the changed component and any directly affected shared layout.

Use representative viewports such as:

- Desktop: **1440 × 1000**
- iPad: **820 × 1180**
- iPhone: **390 × 844**

Check light and dark mode when the changed styles or components can differ by theme.

For a local visual change, inspect the affected component and nearby layout only.

For broad page-layout or responsive work, also inspect:

- overflow;
- navbar/dropdowns;
- project navigation;
- hero;
- Resources;
- At-a-glance;
- article width;
- figures/code/tables;
- related-project section;
- footer.

For substantial responsive work, also check intermediate widths.

If browser tooling is unavailable, complete the relevant build/test validation and explicitly state that visual inspection was not performed.

## Accessibility

Preserve:

- keyboard focus;
- contrast;
- semantic headings;
- usable touch targets;
- reduced-motion support;
- meaningful alt text;
- accessible menus/drawers.

Do not solve responsive problems by hiding important content.

When changing an interactive component, verify keyboard and touch behaviour where relevant.

## Git

Before significant work, inspect the current working state:

```bash
git status
git diff
```

After changes, inspect the resulting diff:

```bash
git diff --stat
git diff
```

Do not create branches, worktrees, commits or rewrite Git state unless the task or workflow calls for it.

Do not rewrite history or discard uncommitted work unless explicitly instructed.

Do not overwrite unrelated user changes.

## Reporting

After completing a task, report:

- the meaningful source changes;
- the validation performed;
- any relevant limitations or checks that could not be run.

For generated sites, distinguish meaningful source changes from generated-output churn when relevant.

For CSS/layout work, identify the canonical source that was changed when this is useful for understanding the fix.

Do not provide a long catalogue of regenerated files unless it is relevant to the task.

Do not suggest or begin unrelated follow-up work unless requested.

## Definition of done

A task is complete when:

- the requested behaviour works;
- the canonical source has been changed rather than generated output patched directly;
- the diff contains only justified changes;
- validation appropriate to the scope of the task has passed.

Additionally, when relevant:

- Quarto renders when rendered output or generation is affected;
- visual identity is preserved unless the task intentionally changes it;
- responsive and theme behaviour remain correct;
- generated output is reproducible;
- relevant interaction, visual or browser tests pass.

For visual tasks, the rendered result is the source of truth.

Once these conditions are met, stop.

## Priority

When instructions conflict:

1. explicit user/task instruction;
2. `AGENTS.md`;
3. `DESIGN.md`;
4. `ARCHITECTURE.md`;
5. established implementation.
